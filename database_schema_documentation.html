1. System Architecture & Core Data Principles

Architecture Foundations
The Gandharva School of Music database is architectured to support real-time audio/video WebRTC classrooms, high-concurrency booking, teacher payout ledgers, course enrollments with flexible EMI schedules, student resource sharing, and verified attendance auditing.

Core Architectural Pillars

1. Strict Referential Integrity: Enforced via PostgreSQL foreign key constraints with cascading deletes for owned sub-entities (e.g. user tokens, teacher availability) and restrictive/set-null semantics on financial audit rows (e.g. payments, enrollments).

2. Precision UTC Timestamps: All temporal records use TIMESTAMP WITH TIME ZONE (Timestamptz 6). Storage occurs strictly in UTC instants; UI localization renders dynamically into viewer timezones with Indian Standard Time (IST) standardized for admin operations.

3. Dual-Ledger Financial Integrity: Monetary balances, course fees, and teacher payouts are stored as Minor Units (Integers) representing Indian Paise (e.g. ₹500 = 50,000 paise). This prevents floating-point rounding errors across payment gateways (Razorpay, UPI) and payout reconciliation.

4. Classroom Auditing & Multi-Join Tracking: Every live lesson maintains both discrete entry/exit logs (teacherJoinedAt, studentJoinedAt) and comprehensive JSON multi-session timelines in attendanceLogs, along with archived in-call chat transcripts in chatLogs.

10. End-to-End System Lifecycles & Data Flows

Data Flow Pipelines

Lifecycle 1: Classroom Session, Attendance & Remuneration Pipeline

1
Session Scheduling: Admin or student schedules class → Lesson record inserted with status SCHEDULED, unique tracking ID (S0017-SE009), and allotted teacher/student.
2
Live Classroom Entry: Student & teacher join LiveKit WebRTC room → /api/lessons/[id]/join logs entry in teacherJoinedAt, studentJoinedAt, and appends timestamp session block to attendanceLogs.
3
In-Call Chat & Recording: Live chat messages persist via /api/lessons/[id]/chat into Lesson.chatLogs. LiveKit composite egress records video to Supabase S3 storage, creating LessonRecording.
4
Departure & Verified Presence: Participants leave → /api/lessons/[id]/leave records exit. Attendance parser verifies mutual co-presence duration. If session meets qualification, marked COMPLETED.
5
Faculty Payout Ledger: If paid course session, remuneration computed based on day rate (₹300) vs night rate (₹500). If free trial, remuneration is strictly ₹0 (excluded from payouts).

Lifecycle 2: Course Enrollment & Financial Ledger Flow

1
Student Admissions Intake: Student selects course → creates CourseEnrollmentRequest with preferred schedule and payment plan (Full, 3-Month EMI, or 6-Month EMI).
2
Razorpay Order Dispatch: Order created via Razorpay API → Payment record created with status CREATED, unique order ID, and amount in minor units (paise).
3
Payment Webhook Verification: Razorpay webhook verifies HMAC signature → updates Payment.status = PAID, sets gatewayPaymentId, and generates custom invoice ID.
4
Academic Contract Provisioning: Enrollment record generated with sessionsRemaining = Course.sessionCount, status ACTIVE, and linked teacher allotted.
